Bolmo, byte by byte

Language models don't read letters. They read tokens, chunks of text picked from a fixed vocabulary. Retrofitting language models to operate over bytes takes a finished token-based model, Olmo 3, and rebuilds it to read and write raw bytes. It keeps almost everything the model learned, for under 1% of the cost of training it.

Context · why this paper exists

Tokens hide the letters

The problem

Nearly every large language model reads subword tokens: chunks like ␣flower or bed, each turned into one ID number. The letters inside a token never reach the model. That hurts tasks about spelling and counting, code, and sequences like DNA. It also makes the vocabulary favour English.

The obvious fix

Read raw bytes, the 0–255 numbers every computer stores text as. Byte-level models exist, but each one was trained from scratch. They trail the best token models, which improve faster than anyone can afford to retrain a byte model to catch up.

This paper's move

Start from a finished token model instead. Keep its transformer, where the knowledge is, and replace only the parts that touch tokens with small byte-level parts. The authors call this byteification. Olmo 3 7B becomes Bolmo 7B. The same recipe turns Qwen3 into Bwen and Llama 3 into Blama.

The key idea · one byte of future

Subword tokenizers secretly look ahead

A language model predicts the next token from past tokens only. But the tokenizer that made those tokens read the whole text first. Whether "W" ends a token depends on what comes after it. Earlier byte-level models placed boundaries from the past alone, so they could not copy a subword model's boundaries. Bolmo's boundary predictor gets to see one byte ahead.

How far ahead must you look?

Run the tokenizer on your text cut off k bytes after each position, and compare its boundary with the boundary from the full text.

0%of boundaries match

With k = 0 every cut ends a token, so a model that sees only the past cannot tell. Cutting and re-running the tokenizer is a crude predictor. Bolmo learns its predictor from the representations of byte t and byte t+1, and gets above 99% with one byte.

Generation · fused vocabulary of 512

Writing one byte at a time

When generating, there is no future byte to peek at. So the language-modelling head predicts the next byte together with whether a patch ends after it: 256 bytes, plus 256 "byte then <b>" entries. The small local models run for every byte. When a fused entry comes out, the patch is complete and the global model runs once. This replays your text as if Bolmo were writing it.

Why fuse the boundary into the byte?

A separate <b> symbol would add k extra positions for the local decoder to process. Doubling the vocabulary from 256 to 512 avoids that. Sampling methods such as top-p work over all 512 entries unchanged. The only cost is a softmax over 512 entries instead of 256.

Prefill is the other path. A prompt you hand the model is complete, so its boundaries come from the predictor that sees one byte ahead.

Training · two stages · 49.1B tokens in total

First copy the subword model, then let go

Bolmo starts from Olmo 3 7B. The global model takes the subword model's transformer layers as they are. The new byte-level parts start from random initialization and are trained in two stages.

9.8B tokens (stage 1, 75K steps) + 39.3B tokens (stage 2, 150K steps), drawn from a 172B-token data mix.

Efficiency · paper Fig. 2 and Extended Data Fig. 3

Bigger patches, fewer global steps

A subword model is tied to its vocabulary. A byte model can make its patches as long as it likes. Bolmo raises bytes per patch by merging subword boundaries away during stage 2. The paper's best merge rule works like BPE run on each example: join the most frequent adjacent pair until the target is reached.

Merging here works on your short text, joining the most frequent adjacent pair of patches (ties go to the shortest result). In the paper it supervises the boundary predictor during training.

Accuracy against compute, 1B models

Values read off the paper's Fig. 2, so expect about ±0.5. t is the target bytes per patch, c the one reached. The subword route (SuperBPE vocabularies) stalls once its softmax gets expensive. Bolmo with BPE merges reaches lower cost at a smaller drop in accuracy.

Decoding speed, 7B models on one H100

Greedy decoding, batch size 1. Values read off Extended Data Fig. 3a (roughly flat across prefill lengths from 4.5K to 72K bytes). At 4.4 bytes per patch, the same as Olmo's tokens, Bolmo is slower. Around 6.6 it overtakes Olmo, in decoding speed and in time to first byte.

Borrowing post-training for free

Task arithmetic, paper Fig. 3

Bolmo's global model is Olmo's transformer, so the weight change that post-training made to Olmo can be added directly: θBolmo + (θIT − θPT). With no extra training this lifts instruction following on IFEval by 36 points, to about where the post-trained Olmo is.

It works when the post-trained model still runs well with its base model's embeddings put back. RL-trained checkpoints, like the one used here, usually do (Extended Data Fig. 2).
